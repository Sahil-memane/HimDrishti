# HimDrishti — GCP Deployment

This is ready-to-run deployment tooling, not a deployment that has already
been performed. Nothing in this repo deploys to GCP on its own — running
`deployment/gcp/deploy.sh` does, and only once you've provided a GCP project
and confirmed you want to proceed (it creates real, billed cloud resources).

## Current local architecture (unchanged)

```
frontend (Vite/React)
    │
    ▼
api-gateway (FastAPI) ──▶ model1-seaice-service (FastAPI + TensorFlow/scikit-learn)
    │                 ──▶ model2-iceberg-service (FastAPI)
    │                 ──▶ model3-routing-service (FastAPI + NetworkX + rasterio)
    ▼
PostgreSQL
```

Each service is independently containerized and communicates over the
network — never merged into one container. This is preserved exactly in the
GCP deployment below.

## What deploys where

| Component | GCP service | Why |
|---|---|---|
| `frontend` | Cloud Run, public | Real static build (see `frontend/Dockerfile.prod`) served by nginx — not the local dev server |
| `api-gateway` | Cloud Run, public | Stateless, holds JWT auth |
| `model1-seaice-service` | Cloud Run, internal-ingress only | TensorFlow + the real trained LSTM/GBR files baked in (`Dockerfile.prod`) |
| `model2-iceberg-service` | Cloud Run, internal-ingress only | Real drift-model config baked in (`Dockerfile.prod`) |
| `model3-routing-service` | Cloud Run, internal-ingress only | Routing + real Sentinel-1 SAR detection, no bundled model files needed |
| `postgres` | Cloud SQL for PostgreSQL 15 | Managed, persistent, automated backups |
| Secrets (`JWT_SECRET`, DB password, `MISTRAL_API_KEY`) | Secret Manager | Auto-generated by `deploy.sh` where possible; never committed |

**Correction from an earlier version of this doc:** this schema does not
actually use PostGIS — every position is stored as plain WKT text (see
`backend/api-gateway/models.py`), and no migration ever runs
`CREATE EXTENSION postgis` or declares a `geometry` column (verified by
grepping `db/migrations/*.sql`). A plain Cloud SQL Postgres instance is
sufficient; no PostGIS-enabled image or extension is required.

**Access pattern:** `frontend` and `api-gateway` are public. `model1`,
`model2`, `model3` are `--ingress=internal` — only reachable from
`api-gateway`'s own service account (granted `roles/run.invoker` on each by
`deploy.sh`), matching how they're only reachable from the gateway locally
via Docker's internal network. Cloud SQL is reached over the private
unix-socket Cloud SQL connector, never a public IP, except briefly during
the one-time migration step (see below).

## What you need to provide

| # | What | How to get it |
|---|---|---|
| 1 | A GCP project with billing enabled | console.cloud.google.com → New Project → note the Project ID; then link a billing account |
| 2 | `gcloud` CLI installed & authenticated | cloud.google.com/sdk/docs/install, then `gcloud init` and `gcloud auth login` |
| 3 | Region | e.g. `asia-south1`; set `GCP_REGION` in `.env.deploy` |
| 4 | Mistral API key *(optional)* | console.mistral.ai → API Keys — only powers Model 3's AI route-explanation text; the app degrades gracefully without it |

DB password and JWT secret are auto-generated by `deploy.sh` and stored only
in Secret Manager unless you set `DB_PASSWORD`/`JWT_SECRET` yourself in
`.env.deploy`.

## Running it

```
cd deployment/gcp
cp .env.deploy.example .env.deploy   # fill in GCP_PROJECT_ID at minimum
./deploy.sh                          # runs every phase in order
```

Or run one phase at a time (useful if something fails partway and you want
to resume): `./deploy.sh <phase>` where phase is one of `apis`,
`artifact-registry`, `secrets`, `cloudsql`, `migrate`, `model1`, `model2`,
`model3`, `gateway`, `frontend`. See the comments at the top of `deploy.sh`
for exactly what each phase does before running it.

The `migrate` phase briefly authorizes this machine's public IP on Cloud SQL
to run `db/migrations/*.sql` via a throwaway `docker run postgres:15 psql`
container, then revokes that authorization again — the deployed Cloud Run
services never use a public IP to reach the database.

## What is NOT done by this tooling

- No service is merged, renamed, or restructured — same 5 services as local.
- No load testing, custom domain, or CDN setup.
- No CI/CD pipeline — `deploy.sh` is run manually, on demand.
- No IAM hardening beyond the minimum (`roles/cloudsql.client` for the
  compute service account, `roles/run.invoker` for api-gateway → models) —
  review before using this for anything beyond a demo/hackathon deployment.
